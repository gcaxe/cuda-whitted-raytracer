## 4. 一致性校验清单（跑完逐条打勾）

- [ ] **档 1~4 之间 `maxDiff` 全部为 0**
      它们只改访存布局和遍历顺序，**不改数学**。任何一档非 0 都是实现 bug，不是"优化近似"。
- [ ] **档 1~4 与档 0（暴力）之间的 `maxDiff`** 可以非 0，但要记录实测值。

      非 0 意味着有子树被丢掉，画面会出现空洞。

- [ ] **三角形数是 10000**（不是 68532），证明用的是 bunny 而不是兜底网格。

## 7. 每档字段是怎么来的（可追溯）

| 字段 | 出处 | 备注 |
| --- | --- | --- |
| 三角形数 | `buildBvh()` 打印的「三角形=」 | AoS 与 SoA 是同一批三角形 |
| 建树(ms) | `buildBvh()` 内 `std::chrono::steady_clock` | 含质心/包围盒预计算、划分与摊平，单线程 CPU |
| 渲染(ms) | `launchTier()` 用 `cudaEventRecord/ElapsedTime` 只包住 kernel | **不含** D2H 拷贝、叠字、存盘 |
| 加速比 | `runBench()`：档 0 的 kernel 时间 ÷ 该档 kernel 时间 | 第 0 行恒为 1.00× |
| maxDiff / 差异像素 | `compareImages()`（`image_io.h`，默认忽略 alpha） | 与档 0 的图逐像素比 |

| 节点数 / 叶子数 / 深度 | `buildBvh()` 的建树统计打印 | 用于解释树质量 |

## 8. 每项优化的机制与预期方向

> 下面写的都是**机制与预期方向**（推导），不是实测值。真实数字填在第 2、3 节，
> 并且要能和这里的方向对上；如果对不上，**以实测为准**，并在第 9 节写清为什么。

### ① 遍历顺序：无序 → 有序遍历 + `best` 剪枝（档 1 → 档 2）

- **前**：固定先左后右，完全不管两个孩子谁离光线更近。
- **后**：先用当前 `best` 测两个孩子盒子的**入口距离 t**，近的先走、远的压栈；
  退栈时如果该节点的入口距离已经 `>= best`，整棵子树直接丢掉，连盒子都不用测。
- **动的是什么**：遍历的**节点访问次数**（算术量基本不变）。
- **预期方向**：渲染时间下降，收益与树的"深度分布"相关。
  先命中近处的物体 → `best` 立刻变小 → 后面那棵远的子树大概率整棵被剪掉。
- **为什么这是干净对照**：档 1 与档 2 只差一个编译期常量 `ORDERED`，
  代码在 `traverseBvh()` 里就是一行 `Ordered ? (tLeft <= tRight) : true`。

### ② 三角形布局：AoS → SoA（档 2 → 档 3）

- **前**：`TriangleAoS` 40 字节连续存放，warp 内 32 个线程各取各的三角形时，地址相隔 40 字节。
- **后**：9 条 `float` 数组 + 1 条 `int` 数组，同一个分量在内存里连续；取一个三角形要读 10 个数组。
- **动的是什么**：访存合并（读的**字节数其实变多**了：10 次标量读 vs 一次 40 字节读）。
- **预期方向**：**不一定变快**。warp 内线程命中同一批叶子三角形时合并更好；
  各走各的叶子时，SoA 会把「一次连续读」拆成 10 次分散读，可能反而更慢。
- 实现要点：`triAt<UseSoA>()` 保证两套布局走同一个 Möller–Trumbore，结果不因布局而变。

### ③ 根节点缓存：全局内存 → `__shared__`（档 3 → 档 4）

- **前**：每个线程每次遍历都从全局内存读根附近的节点。
- **后**：kernel 启动时一个 block 合作读取前 16 个节点（16×32B = 512B）搬进共享内存，
  块内所有线程后续都读片上副本。
- **动的是什么**：访存层次（全局 → 共享）；代价是多一次 `__syncthreads()`。
- **预期方向**：根附近节点确实被反复访问，所以**通常有小幅收益**；但 4070 Ti 的 L1
  本来就能兜住这一小段热点，收益可能很小甚至被同步开销吃掉 —— 以实测为准。

### ④ 节点 32 字节对齐 —— **已在早期版本完成，属于基线**

不是的优化项。`BvhNode` 在 早期版本 就已经是 32 字节
（`bmin[3] + leftOrTriStart` / `bmax[3] + count` 两个 16 字节块），并带
`static_assert(sizeof(BvhNode) == 32)` 钉死。whitted 里还有一个 40 字节的
`BvhNodeNaive`，但它只用于「展示对齐前后的显存差别」，**不在 bench 的 5 档里**。

## 9. 一致性结论与异常说明（跑完必须填）

- 档 1 / 2 / 3 / 4 之间的 `maxDiff`：**15**（程序只测「各档 vs 档 0」；档 1 = 15、档 2/3/4 = 0，故档 1 与档 2 至少差 15）
- 档 1~4 与档 0 之间的 `maxDiff`：**档 1 = 15（差异像素 1 个，占 0.00003%）；档 2 / 3 / 4 均为 0**
- 栈峰值 / 溢出：**11** / 64，溢出 **0** 次
- **实测收益与预期区间的偏差说明**（三项都没达到预期，原因各不相同）：

  **① 有序遍历只有 1.05×（预期 1.5~3×）**

  本场景 BVH 只有 **12 层深**，无序与有序的节点访问次数差距本来就小。
  加上单次 kernel 仅 ~4 ms，**19~27% 的测量噪声**掩盖了 5% 的收益 ——
  两者取值范围完全重叠（档1: 3.86~4.60，档2: 3.69~4.69），**统计上不显著**。
  方向是对的（中位数确实更快），但幅度不足以在噪声中被确认。

  **② SoA 变慢到 0.89×（预期 1.1~1.5×，也允许 <1）**

  SoA 的合并访存只在「warp 内 32 个线程访问相邻三角形」时划算。
  而 **BVH 遍历是随机访问**：不同线程走不同树路径、命中不同叶子，地址本来就分散。
  此时把「一次 48 字节连续读」拆成「10 次独立标量读」，**事务数 ×10 而合并收益为零**。
  这是「优化必须匹配访问模式」的典型反例。

  **③ SMEM 变慢到 0.89×（预期 1.0~1.1×）**

  只缓存 16 个根节点 = **512 字节**，而 4070 Ti 的 **L2 有 48 MB** —— 这些节点本来就常驻 L2。
  共享内存的收益被 `__syncthreads()` 与额外的 occupancy 压力吃掉。

  **④ 共同背景：本场景是 memory-bound**

  BVH 仅 12 层深、三角形数据仅 0.38 MB、显卡有 60 个 SM —— **算力严重过剩**。
  遍历算法层面的微优化被内存延迟淹没。要让这些优化显效，需要提高**算术强度**：
  更大的几何体（树更深）、更多光源（更多阴影光线）、更高的 spp 或递归深度。




## 10. 瓶颈分析（一句话）

**主光线与阴影光线的开销集中在两处：BVH 节点/三角形的访存，以及 Möller–Trumbore 的浮点判定；
的访存优化（有序遍历减少节点数、SoA 改访存模式、共享内存改访存层次）动的都是前者，
所以它们的上限由「访存占比」决定，而后者（每叶子 2~4 次 Möller–Trumbore）会在叶子阈值调小、
树变深时成为新瓶颈。**

展开一点：

- 每像素成本 ≈ 遍历节点数 ×(盒子测试) + 命中叶子数 ×(三角形求交)，两者都要读内存。
- `--debug heatmap` 的亮度就是「每像素访问的节点数」，可以和渲染时间一起解释加速比的来源。
  跑一次 `--debug heatmap`，就能直观看到**有序遍历把访问量压下去了多少**。
- 阴影光线用「命中即返回」的遮挡查询（`occludedBvh`），不需要最近交点，平均访问节点更少；
  但每个着色点都要发一条，绝对开销并不小。
- 递归 `traceRay` 的每一层都要把活跃寄存器压到 local memory，这部分**不随 BVH 优化下降**，
  所以加速比会低于「纯求交次数」的下降倍数（阿姆达尔定律的直观体现）。

## 11. 复现实验时的注意事项

1. 程序已内置预热（bench 前先渲一张 64×64）；手动对比时也应先跑一次再测。
2. 同机器、同驱动、同编译配置下比较；`-arch` 不同会改变寄存器分配。
3. **记录分辨率 / spp / 三角形数**，否则数字之间不可比。
4. 每档的图都叠了参数文字后才存盘，比对用的是**叠字前**的原图（`saveStamped()` 会先复制一份）。
5. 运行目录必须是 `whitted\whitted\`，日志里看到 `三角形数 : 10000` 才算数。
