## ① Möller–Trumbore 的原理

**代码位置**：`triangle.h` 的 `mollerTrumbore()`（核心）、`hitTriangle()`（填 HitRecord、双面法线）、
`hitTriangleAny()`（阴影光线专用的只判命中版本）。

**自己的话**：
三角形上的任意一点都能写成 `v0 + u*(v1-v0) + v*(v2-v0)`，其中 `u>=0, v>=0, u+v<=1`；
光线上的点是 `o + t*d`。让两者相等，就得到一个 3 元一次方程组（未知量 u、v、t）。
Möller–Trumbore 聪明的地方是**不去解这个方程组**，而是用向量三重积把它拆开：

1. `p = cross(d, e2)`，然后 `det = dot(e1, p)`。`det` 就是三边张成的平行六面体体积，
   它等于 0 说明光线方向落在三角形平面内（或者三角形退化了），直接剔除——**这就是唯一的“平行”判断**。
2. `u = dot(s, p) * (1/det)`，`s = o - v0`。用 Cramer 法则可以把 u、v、t 都写成
   三个这样的三重积，分母还都是同一个 `det`，所以只算一次除法。
3. `q = cross(s, e1)`，`v = dot(d, q)/det`，`t = dot(e2, q)/det`。
4. 先算 u、再算 v、最后算 t：**大部分光线在 u 那一步就被剔除了**，后面两次叉积都省了，
   这就是它比“先求平面交点再判内外”快的原因。

两个容易踩的点：一是 `det` 用 `fabsf(det) < eps` 判断，不能只判 `det == 0`（浮点永远不相等）；
二是法线要用 `cross(e1, e2)` 现算，再按 `dot(n, d)` 的符号翻到朝向光线的一侧——三角形是双面的，
不翻的话从背面看过去就是全黑。

## ② BVH 遍历怎么用栈实现

**代码位置**：`bvh.h` 的 `traverseBvh()`（模板核心），外层封装 `intersectBvh()`（最近命中）与
`occludedBvh()`（遮挡查询，命中即返回）；栈就是函数里的 `int stack[64]; float stackT[64];`。

**自己的话**：
递归遍历写成伪代码只有五行，但 GPU 不能这么写（见 ④），所以改成**「一个固定大小的数组当栈 + 一个循环」**：

- 栈里存的是「**还没访问、但已经确认盒子被光线命中**的节点下标」；另外每一层还存一个入口距离 `t`。
- 循环开始时，当前节点的盒子一定是已经判过的，所以**每个节点只做一次盒子测试**：测试是在孩子身上做的 ——
  先测左右孩子的盒子，命中的那个直接下去（不再重复测），另一个压栈。
- **有序遍历**：两个孩子都命中时，比较入口距离 `t`，近的先走、远的压栈。因为 `best`（当前最近命中距离）
  在往下走的过程中会不断变小，先走更可能命中的那一支，另一支就更容易被 `best` 剪掉。
- **退栈时二次剪枝**：弹出前先看 `stackT[sp] < best`，不满足就说明这棵子树不可能有更近的交点，直接丢，
  连盒子测试都省了。这就是「每层存入口距离」的用处。
- 栈深上限是编译期常量（64），每下一层最多压一个节点，所以理论深度不会超过树高（7 万面、叶阈值 4，
  树高约 15 层，余量很大）。
- **压栈必须查溢出**：溢出意味着有一棵子树被悄悄丢掉了，画面会出现空洞。程序里溢出会累加计数，
  kernel 把「栈峰值 + 溢出次数」拷回主机打印，非 0 就告警，绝不静默丢三角形。

## ③ 光线与 AABB 怎么求交

**代码位置**：`bvh.h` 的 `hitAabb()`（slab method）与 `safeInvDir()`（预求倒数方向）；
`AABB` 里的 `area()` / `longestAxis()` 是建树时用的。

**自己的话**：
盒子可以看成三对平行板（x、y、z 各一对）。光线和一对板相交会得到一个区间 `[t0, t1]`，
和盒子相交就是**三个区间求交集**：

```
near = max(三对板里较小的那个, tMin)
far  = min(三对板里较大的那个, tMax)
命中  ⟺  near <= far
```

两个关键工程细节：

1. **预求 `invD = 1/d`**，然后写 `(bmin - o) * invD`，而不是 `(bmin - o) / d`。
   一次除法换成三次乘法，而且除法在 GPU 上慢得多。
2. **不特判「方向分量为 0」**。`1/0` 在 IEEE-754 里是 `±inf`，
   `(bmin-o)*inf` 要么是 `+inf` 要么是 `-inf`，三对板求交之后：光线在板内就完全不受影响，
   在板外区间直接变空。也就是说**除零由 IEEE 语义自然处理**。真正要小心的是
   `0 * inf = NaN`（原点正好落在板面上且方向分量为 0），这里靠 `fminf/fmaxf` 的
   「忽略 NaN 操作数」语义把它吃掉，所以也不需要额外判断。

返回值我多给了一个 `tEntry`（进入盒子的距离）：有序遍历要靠它决定先走哪个孩子，
而 `fminf` 的结果本来就算出来了，多输出一个 float 几乎没有代价。

## ④ 为什么 GPU 上递归不好用

**代码位置**：`kernel.cu` 的 `traceRay()`（**故意保留递归**，Whitted 模型直译）与
`bvh.h` 的 `traverseBvh()`（**改成显式栈的对照实现**）；栈使用统计在 `renderKernel()` 里归约。

**自己的话**：
三件事叠在一起：

1. **寄存器**：递归函数不能被内联（编译器不知道会递归多少层），每一层的活跃变量必须在调用点
   保存下来，通常落到 local memory —— 而 local memory 物理上就在显存里，一次递归就是一次显存往返。
2. **分歧**：一个 warp 里 32 个线程的光线路径不同，递归深度也不同。深度不一致时，
   硬件要么串行化各分支，要么让浅的线程空等，占用率直接掉下来。
3. **不可预测**：编译器无法为递归函数做寄存器分配和调度优化（栈帧大小动态），
   而 GPU 的性能极度依赖「寄存器数固定 → 占用率已知 → 访存能藏住」。

所以工业界的做法是：**把「每条光线都要跑很多次」的遍历改成显式栈的迭代实现**（BVH 遍历就是典型，
栈深度上限编译期已知，寄存器可预测），而把真正的递归留在着色那一层。本项目就是这么分工的：
`traverseBvh()` 是显式栈，`traceRay()` 保持递归以对应 Whitted 的光线树结构，
并且用 `--depth` 把递归深度卡在 1~16 —— 这也解释了为什么「BVH 优化的加速比」会被
不随优化下降的着色递归开销摊薄。

如果读者追问「那你会怎么彻底去掉递归」：把递归改成显式栈 + 状态机，
光线弹射变成「压入待处理的光线任务」，代价是代码复杂度上升、可读性下降，
在 Whitted 这种深度 5 左右、分支固定（最多一反射一折射）的场景里收益有限，不值得。

## ⑤ 怎么处理 shadow acne

**代码位置**：`materials.h` 的 `inShadow()`（构造阴影光线 + epsilon 偏移）、
`rt_math.h` 的 `RT_SHADOW_EPS` 常量、`kernel.cu` 的 `traceRay()`（反射/折射光线的偏移与
`frontFace` 法线翻转）。

**自己的话**：
shadow acne（阴影粉刺/条纹）的本质是**自交**：阴影光线的起点就在着色点的表面上，
浮点误差让「起点到光源」这条线又打回了自己所在的那个三角形/球面，于是本不该有阴影的地方出现条纹。
处理办法是三层：

1. **沿法线抬起起点**：`origin = p + n * RT_SHADOW_EPS`。这是最直接也最有效的一招。
   epsilon 太大太小都不行：太小还自交（acne），太大就会出现「阴影和物体分离 / 漏光」
   （peter-panning、light leak）。本项目取 `1e-3`（场景尺度约 2~3 个单位）。
2. **同时收窄 t 区间**：`inShadow()` 里用 `[RT_SHADOW_EPS, dist - RT_SHADOW_EPS]`。
   终点也缩一点，避免「光源正好在表面另一侧」被算成遮挡。
3. **反射/折射光线用不同的偏移方式**：反射沿法线抬（`p + n*eps`）；
   折射沿折射方向抬（`p + refracted*eps`）——因为折射光线会穿到表面内侧，
   沿法线抬反而可能把它留在错误的一侧。另外法线永远按 `dot(d, n)` 翻到与入射方向相对的一侧，
   这样从物体内部射出的光线才不会立刻又打到自己。

如果读者问「有没有比固定 epsilon 更好的」：有，常见的是
**按几何尺度缩放的 epsilon**（`eps * max(1, |p|)`）、**整数/双精度 t 排序**，
或者干脆用「自交过滤」（记录上一次命中的图元 id 并跳过）。

## ⑥ 加速比怎么来的、瓶颈在哪

**代码位置**：`kernel.cu` 的 `runBench()`（五档循环 + `compareImages()` 逐像素校验）、
`launchTier()`（只对 kernel 计时）；被计时的东西在 `bvh.h` 的 `buildBvh()` / `traverseBvh()` /
`fetchNode()` 与 `triangle.h` 的 `triAt()`。

**自己的话**：
加速比的分子是**暴力遍历**：每个像素对全部三角形做一次 Möller–Trumbore，复杂度 O(像素数 × 三角形数)，
所以 7 万面、720p 就是几千亿次求交，慢得理直气壮。分母是 BVH：每条光线平均只访问
「树高 + 少量子树」个节点、只对命中的 2~4 个叶子三角形做精确求交，复杂度降到 O(像素数 × log 三角形数)。

具体是这么测的（也是被追问时要能说清的口径）：

- **只对 kernel 计时**：`cudaEventRecord` 包住 `<<<>>>`，D2H 拷贝、叠字、存盘都不算 ——
  否则测的是 PCIe 带宽不是渲染器。
- **同一场景、同一相机、同一随机种子**，并且先跑一张小图预热，避免把首次启动开销算进第一档。
- **每档都与第 0 档逐像素比对**（`compareImages()`）：加速不等于画错，`maxDiff` 一起报出来。
- 建树时间**单列一列**：BVH 是「一次建树、多次渲染」的结构，转台 8 张图时建树只付一次。

瓶颈在哪：的三项优化（**有序遍历**、SoA、共享内存根缓存）**动的都是"访问多少次 / 怎么访问"**——
有序遍历减少访问的节点数，SoA 改三角形访存模式，共享内存改节点访存层次。
所以它们收益的上限由「节点/三角形访存的占比」决定；剩下的是纯粹的求交计算
（每个叶子 2~4 次 Möller–Trumbore）和不随 BVH 变化的着色递归开销。
判断当前卡在哪一边的土办法：用 `--debug heatmap` 看每像素访问的节点数
（访存压力），再对比把 `--depth` 从 5 降到 1 之后的时间差（着色递归占比）。
想再快，方向是「减少节点访问次数」（更好的划分、压缩节点、光线打包/SIMD）
而不是「把 Möller–Trumbore 再优化几个 flop」。

> **实测结果**（2026-11-04，Release x64，2560 × 1440，10000 面，6 次中位数）：
>
> | 档 | 渲染(ms) | 加速比 | 极差 |
> | --- | --- | --- | --- |
> | 0 暴力 AoS | 1305.58 | 1.0× | 1.01× |
> | 1 无序遍历 | 3.98 | 328.4× | 1.19× |
> | **2 有序遍历** | **3.78** | **345.4×** | 1.27× |
> | 3 + SoA | 4.24 | 308.3× | 1.27× |
> | 4 + SMEM | 4.78 | 273.1× | 1.37× |
>
> **三项优化里只有有序遍历方向正确（1.05×），SoA 和 SMEM 反而都变慢了（0.89×）。**
> 这不是实现错误，而是**本场景是 memory-bound**：
> - BVH 仅 **12 层深** → 无序/有序的节点访问次数差距本来就小
> - 三角形数据仅 **0.38 MB** → 本来就在 L2（48 MB）里
> - **60 个 SM 算力过剩** → 微优化被内存延迟淹没
>
> **可以主动讲这段（比只报加速比有说服力得多）**：
>
> > "我实测了 SoA，结果比 AoS 慢 11%。原因是 BVH 遍历是**随机访问** ——
> > warp 内 32 个线程走不同树路径、命中不同叶子，地址本来就分散，
> > 合并访存（coalescing）根本没机会发生。把「一次 48 字节连续读」拆成
> > 「10 次独立标量读」，事务数 ×10 而收益为零。
> >
> > 教科书说 SoA 更好，前提是「线程访问相邻数据」；我的场景不满足这个前提。
> > 这让我理解到：**优化必须匹配实际的访问模式，不能照搬结论。**"
>
> 这个"负面结果"是**加分项**：它证明你做了真实实验、能识别瓶颈类型
> （memory-bound vs compute-bound）、知道优化失效的原因，而不是"我用了 SoA 所以快了"。

> 注意**节点 32 字节对齐不是的优化**：它在早期版本就做完了（`BvhNode` 用
> `bmin[3]+leftOrTriStart` / `bmax[3]+count` 两个 16 字节块，带 `static_assert`），
> 它是**基线**。说「我做了 32B 对齐」没问题，但要说清那是早期版本的成果，
> 做的是在它之上量化「有序遍历 / SoA / 共享内存」各自值多少。
